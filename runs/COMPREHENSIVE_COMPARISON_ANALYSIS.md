## 三、深层次问题分析

### 3.1 为什么Run 2比Run 1更快收敛到RSU单一模式？

#### 原因1: Critic学习率降低的反作用

**预期效果**: 降低lr_critic应该减缓收敛，提升稳定性  
**实际效果**: 反而加速了向RSU的收敛

**机制分析**:
```
Run 1 (lr_critic=5e-4):
- Critic快速学习 → 价值估计波动大 → Actor探索更多
- 梯度爆炸 → 训练不稳定 → 策略更新方向多变
- 结果: 保持了一定的Local探索 (21%)

Run 2 (lr_critic=2e-4):
- Critic慢速学习 → 价值估计更稳定 → Actor更信任Critic
- 训练稳定 → 策略更新方向一致 → 快速收敛到局部最优
- 结果: 快速锁定RSU (99.86%)
```

**悖论**: 更稳定的训练反而导致更差的探索！

#### 原因2: 熵系数提升未达预期

**Run 1**: entropy_coef = 0.012  
**Run 2**: entropy_coef = 0.02 (↑67%)

**预期**: 更高的熵系数应该增强探索  
**实际**: Run 2的策略熵反而更低 (0.293 vs 0.3414)

**原因**:
1. **熵正则化的局限性**: 当RSU的Q值显著高于其他动作时，即使有熵正则化，策略仍会收敛到RSU
2. **权重对比**: entropy_coef=0.02 相比 W_TIME=0.35 太小 (仅5.7%)
3. **数学本质**:
   ```
   策略目标: max E[R] + α·H(π)
   当 Q(RSU) >> Q(Local/V2V) 时:
   即使 α=0.02，最优策略仍是 π(RSU) ≈ 1
   ```

#### 原因3: 初始探索不足

**Run 1**: 初期Local占比57.55%，有充分的Local经验  
**Run 2**: 初期Local占比仅8.8%，缺乏Local经验

**影响**:
- Run 1的Actor学习到了Local的价值，即使后期也保持21%
- Run 2的Actor从未充分体验Local，快速放弃探索

### 3.2 两次训练的共同问题

#### 问题1: RSU的结构性优势过于显著

**环境配置问题**:
```
RSU算力: 6 GHz × 4核 = 24 GHz
车辆算力: 1.0-1.8 GHz (平均1.4 GHz)
算力比: RSU是车辆的 17-24倍

任务完成时间估算 (1 Gcycles任务):
- RSU: 1G / 6G = 0.167s
- 车辆Local: 1G / 1.4G = 0.714s (4.3倍慢)
- V2V: 通信 + 0.714s + 链路风险
```

**结论**: 在当前环境配置下，RSU是**客观最优解**，智能体学习到"全部卸载RSU"是**正确的策略**。

#### 问题2: 奖励函数未充分惩罚RSU过载

**当前奖励设计**:
```python
W_TIME = 0.35      # 时间主导
W_ENERGY = 0.05    # 能耗权重太低
W_INTERF = 0.03    # 干扰权重太低
```

**问题**:
1. 时间权重0.35远高于能耗0.05，智能体优先优化完成时间
2. RSU队列惩罚不足，分摊到单个决策的惩罚微弱
3. 缺乏显式的"RSU过载惩罚"项

**数值示例**:
```
假设任务A:
- RSU卸载: 时间1.5s, 能耗0.01J 
  → reward ≈ -0.35×1.5 - 0.05×0.01 = -0.525
- Local执行: 时间2.0s, 能耗0.005J 
  → reward ≈ -0.35×2.0 - 0.05×0.005 = -0.700

RSU奖励更高 → 智能体选择RSU
```

即使RSU队列已有10个任务，增加的等待时间惩罚仍不足以让Local成为更优选择。

#### 问题3: Oracle匹配率低 (Run 1)

**Run 1的Oracle匹配率仅30.73%**，说明:
1. 策略决策质量不够优
2. Oracle建议V2V但选择RSU的比例高达58.29%
3. 存在较大的改进空间

**原因**:
- Oracle可能基于理想假设 (无通信延迟、无链路中断)
- 实际环境中V2V的不确定性高，智能体学习到避免V2V
- 奖励函数与Oracle目标不完全一致

## 四、根本问题诊断

### 4.1 环境设计与算法目标不匹配

**环境设计**: RSU算力过强、车辆过弱、任务负载不足  
**算法目标**: 最小化任务完成时间 + 能耗  
**实际需求**: 负载均衡、资源利用多样化、避免单点过载

**矛盾点**:
- 如果目标是最小化完成时间，RSU确实是最优选择
- 如果目标是负载均衡，需要显式建模RSU过载惩罚
- 当前奖励函数未明确表达"避免RSU过载"的需求

### 4.2 奖励函数设计缺陷

**当前方案**: progress + term + illegal

**缺失项**:
1. **RSU过载惩罚**: 未显式惩罚RSU队列过长
2. **负载均衡奖励**: 未奖励动作多样性
3. **V2V协作激励**: 未充分激励V2V协作
4. **信誉风险项**: 虽然保留但权重为0

**权重失衡**:
- W_TIME (0.35) 主导决策

### 4.3 探索-利用平衡失效

**Run 1**: 梯度爆炸反而保持了探索 (意外的好处)  
**Run 2**: 训练稳定但探索不足 (稳定性的代价)

**问题**:
1. 熵系数太低 (0.02 vs W_TIME=0.35)

#### 方案B: 新增RSU过载惩罚项

```python
# 新增配置
W_RSU_OVERLOAD = 0.15  # RSU过载惩罚权重

def compute_rsu_overload_penalty(rsu_queue_cycles, threshold=5e9):
    """
    RSU队列长度超过阈值时施加二次惩罚
    threshold: 5 GCycles (约0.83s @ 6GHz)
    """
    if rsu_queue_cycles > threshold:
        excess_ratio = (rsu_queue_cycles - threshold) / threshold
        penalty = -0.5 * (excess_ratio ** 2)  # 二次惩罚
    else:
        penalty = 0.0
    return penalty

# 在奖励计算中加入
reward = r_progress + r_term + r_illegal + W_RSU_OVERLOAD * rsu_penalty
```

**效果**: 直接惩罚RSU过载，迫使智能体分散负载
