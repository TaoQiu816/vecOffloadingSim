## 三、问题诊断

### 3.1 Run 2的性能劣化原因

**问题1: 过度依赖RSU导致性能下降**

虽然RSU队列利用率相近（17%），但Run 2的性能明显更差：
- 任务成功率低5.9%
- 完成时间长0.22s
- 超时率高6.2%

**可能原因**:
1. **缺乏灵活性**: 99.9% RSU策略无法适应不同场景
   - 简单任务也卸载RSU，浪费通信时间
   - 车辆距离RSU远时仍强行卸载，通信延迟高
   - 无法利用车辆空闲算力

2. **能耗增加39%**:
   - Local执行能耗最低（无通信）
   - RSU卸载需要V2I通信，能耗更高
   - Run 2几乎不用Local，能耗显著增加

3. **性能波动大**:
   - 单一策略对环境变化敏感
   - 成功率标准差0.178（Run 1为0.077）

**问题2: 策略过早收敛**

Run 2在200 ep就达到99% RSU占比，之后不再探索：
- 可能错过了更优的混合策略
- Run 1在800 ep才稳定在77% RSU，有更充分的探索

### 3.2 Run 1的优势

**优势1: 负载分配更合理**

77% RSU + 21% Local的混合策略：
- 复杂任务卸载RSU（利用高算力）
- 简单任务Local执行（节省通信时间和能耗）
- 整体性能更优

**优势2: 鲁棒性更强**

- 策略更灵活，适应不同场景
- 性能波动小（成功率标准差0.077）

**优势3: 能耗更低**

- 21% Local动作节省通信能耗
- 总能耗比Run 2低39%

## 四、参数影响分析

### 4.1 Critic学习率的影响

**降低Critic学习率 (5e-4 → 2e-4) 的效果**:

**理论预期**:
- Critic更新更慢 → 价值估计更保守 → 策略更新更谨慎

**实际效果**:
- Run 2收敛更快（200 ep vs 800 ep）
- 策略更确定（RSU占比标准差0.004 vs 0.147）
- 但性能更差

**原因分析**:

较低的Critic学习率导致价值估计更快稳定：
1. 早期经验对价值估计影响更持久
2. 如果早期经验偏向RSU，价值估计会快速固化
3. Actor基于稳定的价值估计快速收敛

较高的Critic学习率保持价值估计的灵活性：
1. 持续根据新经验调整价值估计
2. 给Actor更多探索空间
3. 最终找到更优的混合策略

### 4.2 熵系数的影响

**提升熵系数 (0.012 → 0.02) 的效果**:

**理论预期**:
- 熵正则化更强 → 策略更分散 → 探索更多

**实际效果**:
- Run 2的策略熵反而更低（0.286 vs 0.341）
- 动作分布更集中（99.9% RSU）

**原因分析**:

熵正则化的局限性：
1. 熵系数只能鼓励策略分散，不能改变动作的相对价值
2. 当RSU的Q值显著高于其他动作时，即使有熵正则化，最优策略仍是集中在RSU
3. 0.02的熵系数相比时间奖励权重0.35仍然太小（仅5.7%）

**关键洞察**:
- 熵系数0.012在Run 1中反而效果更好
- 可能是因为配合较高的Critic学习率，保持了价值估计的不确定性
- 这种不确定性本身就是一种"隐式探索"

### 4.3 参数交互效应

**Run 1 (LR_critic=5e-4, entropy=0.012)**:
- 高学习率 → 价值估计持续调整 → 策略持续探索
- 适中熵系数 → 不过度强制分散 → 自然找到平衡

**Run 2 (LR_critic=2e-4, entropy=0.02)**:
- 低学习率 → 价值估计快速固化 → 策略快速收敛
- 高熵系数 → 无法对抗固化的价值估计 → 失效

**结论**: 参数之间存在交互效应，不能孤立调整。

## 五、环境合理性分析

### 5.1 当前环境是否合理？

**RSU算力配置**:
- 6 GHz × 4核 = 24 GHz
- 是车辆平均算力(1.4 GHz)的17倍

**问题**: 这个配置是否符合实际？

**现实参考**:
- 边缘服务器: 通常8-16核, 2-3 GHz, 总算力16-48 GHz
- 车载计算单元: 1-2 GHz (嵌入式), 高端可达3-4 GHz
- 实际算力比: 约10-20倍

**结论**: 当前配置(17倍)在合理范围内。

### 5.2 为什么Run 1的混合策略更优？

**关键发现**: RSU队列利用率仅17%，远未饱和（容量30 GCycles）

这说明：
1. **RSU资源充足**: 不存在过载问题
2. **通信开销是瓶颈**: 不是计算能力

**任务完成时间分解**:
```
总时间 = 通信时间 + 计算时间 + 等待时间

RSU卸载: T_comm(V2I) + T_comp(RSU) + T_wait(queue)
Local执行: 0 + T_comp(Local) + 0
```

**对于简单任务**:
- 计算量小（如0.5 GCycles）
- Local执行: 0.5/1.4 = 0.36s
- RSU卸载: 通信0.1s + 计算0.5/6=0.08s + 等待0.05s = 0.23s

看似RSU更快，但考虑实际因素：
- V2I通信受距离、干扰影响，实际可能>0.1s
- RSU队列等待时间波动
- 通信失败重传

**对于复杂任务**:
- 计算量大（如3 GCycles）
- Local执行: 3/1.4 = 2.14s
- RSU卸载: 通信0.15s + 计算3/6=0.5s + 等待0.1s = 0.75s

RSU明显更优。

**Run 1的智能之处**:
- 学会了区分简单/复杂任务
- 简单任务Local执行（21%）
- 复杂任务RSU卸载（77%）
- 这是一个**任务感知的自适应策略**

### 5.3 Run 2为什么性能更差？

虽然99.9% RSU策略在理论上应该利用RSU的高算力，但实际性能更差：

**原因1: 通信开销被低估**

奖励函数中时间权重0.35主导，但：
- 时间计算可能未充分考虑通信不确定性
- 实际通信时间受距离、干扰、重传影响
- 简单任务的通信开销占比更高

**原因2: 缺乏任务区分**

Run 2的单一策略无法区分：
- 简单 vs 复杂任务
- 近距离 vs 远距离车辆
- 低负载 vs 高负载时段

**原因3: 能耗增加**

虽然能耗权重仅0.05，但：
- Run 2能耗增加39%
- 对总奖励的负面贡献: 0.019 × 0.05 = 0.001
- 看似很小，但累积效应显著

### 6.2 中期建议（微调参数）

**建议1: 动态熵系数**

```python
# 根据动作分布自适应调整
def update_entropy_coef(episode, rsu_ratio):
    if rsu_ratio > 0.85:
        # RSU占比过高，增加探索
        ENTROPY_COEF = min(0.03, ENTROPY_COEF * 1.05)
    elif rsu_ratio < 0.65:
        # RSU占比过低，减少探索
        ENTROPY_COEF = max(0.01, ENTROPY_COEF * 0.95)
    return ENTROPY_COEF
```

**理由**: 自适应调整，维持动作平衡。

**建议2: 增强Local动作的Logit Bias**

```python
LOGIT_BIAS_LOCAL = 0.2   # 从0.1提升到0.2
LOGIT_BIAS_RSU = -0.1    # 从0.0降到-0.1
```

**理由**:
- 当前bias (Local=0.1, RSU=0.0)可能不足
- 适度增强Local先验，抑制RSU先验

**建议3: 调整奖励权重**

```python
W_TIME = 0.30      # 从0.35降低
W_ENERGY = 0.10    # 从0.05提升
```

**理由**:
- 提升能耗权重，激励Local执行
- 降低时间权重，减少对RSU的过度偏好
- 保持总权重平衡

### 6.3 长期建议（优化环境）

**建议1: 引入任务分类**

在观测空间中增加任务复杂度特征：
```python
# 在任务特征中增加
```

**理由**: 帮助智能体学习任务感知策略。

**建议2: 细化通信模型**

考虑更真实的通信延迟：
```python
# 增加通信不确定性
comm_delay = base_delay * (1 + random.uniform(-0.2, 0.3))
```

**理由**: 更准确反映通信开销，避免低估。

**建议3: 增加RSU负载惩罚**

虽然当前队列利用率仅17%，但可以预防性地增加：
```python
# 在奖励函数中增加
if rsu_queue > threshold:

```

**理由**: 鼓励负载分散，提升鲁棒性。

### 6.4 不建议的修改

**不建议1: 大幅降低RSU算力**

- 当前17倍算力比在合理范围内
- 大幅降低会偏离实际场景

**不建议3: 继续降低Critic学习率**

- Run 2已证明2e-4导致过快收敛
